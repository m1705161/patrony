# Лекция 1 — Архитектурные паттерны: шардирование, репликация — как теория переходит в инженерные расчёты

> Стек курса: Kafka, Spark, Kubernetes, Lakehouse (Iceberg), Trino, S3, Greenplum, Postgres.
> Акцент практики — Postgres: нативные партиции, Citus, Patroni/etcd.
> Без привязки к часам. Формат — структурированный конспект.

## 1. История и мотивация
- От монолитной БД на одной машине к распределённым системам: вертикальное vs горизонтальное масштабирование.
- CAP-теорема (Brewer, 2000; Gilbert–Lynch, 2002), PACELC.
- Появление MPP-хранилищ (Teradata, Greenplum), NoSQL (Dynamo, Cassandra, BigTable), NewSQL (Spanner, CockroachDB).
- Зачем в курсе: Greenplum (MPP), Spark (партиции), Iceberg (скрытое партиционирование) — везде одни и те же паттерны.

## 2. Теория шардирования
- Понятия: шардинг = горизонтальное партиционирование данных по узлам.
- Стратегии: hash, range, directory/list, consistent hashing.
- Shard key: как выбирать, кардинальность, skew/hot spot.
- Rebalancing / resharding, why it's expensive.
- Партиционирование vs шардирование (логическое vs физическое).

## 3. Теория репликации
- Модели: leader–follower (primary–replica), multi-leader, leaderless (quorum).
- Синхронная vs асинхронная репликация, trade-off.
- Quorum: R + W > N, read/write quorum.
- Консенсус кратко: Raft / Paxos (зачем, когда нужен — leader election, Patroni/etcd).
- Модели согласованности: strong, eventual, causal, read-your-writes, monotonic reads.

## 4. Переход теории в инженерные расчёты на Postgres (ядро лекции)

### Партиционирование (на уровне одного Postgres)
- Нативные декларативные партиции: RANGE / LIST / HASH.
- Выбор partition key и partition pruning — как планировщик отсекает партиции в запросе.
- Расчёт: сколько партиций нужно (по объёму на партицию и retention-окну), влияние числа партиций на планировщик и autovacuum, размер индексов.

### Шардирование через Citus
- Coordinator + workers, distribution column (= hash-шардинг на уровне узлов).
- Расчёт: число воркеров под объём/QPS, `shard_count` (по умолчанию 32) × `shard_replication_factor`, распределение строк по шардам, цена rebalance.

### Репликация в Postgres
- Streaming (physical) replication: поток WAL, standby, lag через `pg_stat_replication`.
- Логическая репликация (публикации/подписки) — выборочные таблицы, без физического копирования всего.
- Расчёт: lag в сек/байтах; `synchronous_commit` (on / remote_apply) → trade-off «задержка vs гарантия доставки».

### HA: Patroni + etcd
- Leader election через etcd (RAFT), ручной и автоматический failover.
- RTO = время failover (обнаружение сбоя + промоут нового primary).
- RPO = потеря транзакций при async (коммиты, не успевшие доехать до standby).

### Расчёт сети и хранилища
- Сеть: `write_rate × replication_factor` (+ basebackup при репликации с нуля).
- Storage amplification: replication_factor; полные копии standby.

### Числовой пример «от данных к железу»
- Дано: N ТБ + X QPS + бюджеты по RPO/RTO → считаем: воркеры Citus, партиции, число standby-реплик, допустимый replication lag, сетевой канал, что из этого закрывает Patroni.

## 5. Примеры на стеке курса
- Greenplum: distribution key (= шардинг по hash), segment mirror (= репликация), gp_segment_id, rebalance.
- Postgres: нативные партиции (range/list/hash), logical replication, Citus (distributed tables), Patroni/etcd (HA, leader election).
- Spark: партиции RDD/DataFrame, repartition/coalesce, data skew в joins, broadcast vs shuffle.
- S3: репликация объектов (CRR/SRR), сильная согласованность (с 2020), eventual vs strong.
- Trino: параллелизм, hash partitioning при join/aggregation, распределённый запрос поверх шардов.
- Kubernetes: ReplicaSet/replicas, StatefulSet для БД, PodDisruptionBudget, spread across nodes.

- Patroni + etcd — сломать primary, увидеть failover (leader election).
