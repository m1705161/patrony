# Лекция 1 — Архитектурные паттерны: шардирование, репликация — как теория переходит в инженерные расчёты

> Стек курса: Kafka, Spark, Kubernetes, Lakehouse (Iceberg), Trino, S3 (MinIO), Greenplum, Postgres.
> Формат — структурированный конспект: тезисы, схемы, таблицы, формулы, конкретные цифры.
> Ключевая идея лекции: **шардирование и репликация — это два ортогональных паттерна**. Шардирование отвечает на вопрос «как разложить данные по узлам, чтобы влезли и обрабатывались параллельно», репликация — на вопрос «как пережить отказ узла и не потерять данные». Инженерная работа — перевести оба требования в **числа**: сколько шардов, сколько реплик, какой сетевой трафик, какое RPO/RTO, какая доступность.

---

## 1. История и мотивация

### 1.1. Монолит → распределённые системы

**Вертикальное масштабирование (scale-up):** больше CPU/RAM/дисков в одну машину.

- Плюсы: простота (один сервер, одна СУБД, транзакции локальны), нет сетевых задержек.
- Минусы: цена растёт нелинейно (топовые серверы стоят в разы дороже), есть физический потолок (ядра, RAM, шина ввода-вывода), одна точка отказа — падает всё сразу.
- Реальная цифра: один сервер «всё в памяти» может держать сотни ГБ–единицы ТБ RAM, но дальше цена/TB резко растёт.

**Горизонтальное масштабирование (scale-out):** много обычных (commodity) машин.

- Данные режут на части и разносят по узлам — это **шардирование**.
- Каждую часть копируют на несколько узлов — это **репликация**.
- Платим: сеть (передача данных между узлами), распределённая координация (согласованность), сложность эксплуатации.

**Почему это стало неизбежно:**
- Объёмы данных выросли с ГБ до ПБ (веб-логи, телеметрия, аналитика).
- Один диск = ~100–250 MB/s последовательного чтения; ПБ на одном узле читается часами. Параллелизм по сотням дисков даёт десятки ГБ/с.
- Отказ узла — штатное событие, а не катастрофа (при сотнях машин что-то ломается ежедневно).

### 1.2. CAP-теорема (Brewer 2000; доказательство Gilbert–Lynch 2002)

> В распределённой системе при **сетевом разделении (Partition)** нельзя одновременно гарантировать **Consistency** (все узлы видят одни и те же данные) и **Availability** (каждый запрос получает ответ). Можно выбрать **C или A**; P — не опция, сеть падает всегда.

| Выбор | Что это значит | Примеры |
|---|---|---|
| **CP** (consistency при разделении) | При разделении жертвуем доступностью: часть запросов блокируется/ошибается | Spanner, HBase, etcd, ZooKeeper, Greenplum (отказ сегмента → запросы с ошибкой) |
| **AP** (availability при разделении) | При разделении жертвуем согласованностью: отвечаем, но данные могут быть устаревшими | Dynamo, Cassandra (tunable), CouchDB |

Ключевые оговорки:
- CAP описывает **только поведение при сетевом разделении**, а не «всегда выбирай два из трёх». Без разделения система может быть и C, и A одновременно.
- «Consistency» в CAP — это **линеаризуемость** (сильнейшая модель), а не «согласованность вообще».

### 1.3. PACELC (Abadi, 2012) — уточнение CAP

> **Если есть Partition (P)** → выбор между **A** и **C** (как в CAP).
> **Иначе (E, no partition)** → выбор между **Latency (L)** и **Consistency (C)**.

Смысл: разделение случается **редко**, а штатный режим — **постоянно**. Поэтому trade-off «задержка против согласованности» в нормальной работе часто важнее, чем CAP-выбор. Каждый реплицированный чтение-запись на согласованность добавляет сетевой round-trip — это и есть цена C.

Классификация систем по PACELC:

| Система | PACELC | Пояснение |
|---|---|---|
| Cassandra, DynamoDB (default), Riak | **PA/EL** | при разделении — доступность; в штатном режиме — низкая задержка (слабая согласованность) |
| Spanner, CockroachDB (default) | **PC/EC** | согласованность и при разделении, и в штатном режиме (платим задержкой) |
| MongoDB (default), Postgres sync-replication | **PC/EC** | согласованность приоритетна |

### 1.4. Три поколения систем

| Класс | Идея | Представители | Шардирование / репликация |
|---|---|---|---|
| **MPP** (massively parallel processing) | Shared-nothing аналитика, данные заранее разложены по сегментам | Teradata, Greenplum, Vertica | Hash/random distribution + segment mirrors |
| **NoSQL** (Dynamo-style / BigTable-style) | Горизонтально масштабируемые KV/широкие таблицы, слабая согласованность | Dynamo, Cassandra, BigTable, HBase, MongoDB | Consistent hashing / range + quorum-репликация |
| **NewSQL** | SQL + ACID-транзакции на кластере, сильная согласованность | Spanner, CockroachDB, TiDB | Range-sharding + Paxos/Raft-репликация |

### 1.5. Зачем в курсе (связь со стеком)

Один и тот же паттерн «раздели + скопируй» встречается везде:
- **Greenplum** — MPP: `DISTRIBUTED BY` = шардирование, segment mirror = репликация.
- **Kafka** — партиции топика = шарды лога (упорядоченность внутри партиции, масштабирование по числу партиций).
- **Spark** — партиции RDD/DataFrame = логические шарды, repartition/coalesce = управление ими.
- **Iceberg** — скрытое партиционирование = декларативное шардирование таблицы на уровне файлов.
- **Trino** — hash partitioning при join/aggregation = переразложение данных «на лету» между воркерами.
- **S3/MinIO** — объектное хранилище: шардирование «спрятано» внутри, репликация/erasure coding — наружу.
- **Kubernetes** — replicas = репликация приложения, StatefulSet = стабильная идентичность для БД-шардов.

## 2. Теория шардирования

### 2.1. Определения

- **Шардинг (sharding)** = горизонтальное партиционирование данных **по узлам**: строки таблицы/записи распределяются между несколькими серверами, каждый хранит и обслуживает свою часть.
- **Партиционирование vs шардирование:**
  - **Партиционирование** — логическое деление таблицы (может быть внутри одного сервера, например нативные партиции Postgres).
  - **Шардирование** — физическое: партиции лежат на **разных машинах**.
  - Правило: «шардинг = партиционирование + распределение по узлам». Все шарды — партиции, не все партиции — шарды.

### 2.2. Стратегии распределения

| Стратегия | Как работает | Плюсы | Минусы |
|---|---|---|---|
| **Hash** | `node = hash(key) mod N` | Равномерно (при хорошем key), детерминированно, точка-чтение O(1) | Range-запросы идут на **все** узлы; `N` менять дорого (mod N меняет все mapping'и) |
| **Range** | Узлы владеют непрерывными диапазонами ключей (A–M, N–Z или по датам) | Range-сканы локальны, добавление узла = перенос части диапазонов | **Hot spot**: ключи с временной/лексикографической корреляцией бьют в один узел |
| **Directory / list** | Явная таблица соответствия «значение → узел» (tenant_id → shard) | Полный контроль, можно двигать один tenant | Метаданные сами становятся узким местом; нужен каталог |
| **Consistent hashing** | Узлы и ключи хэшируются на кольцо [0, 2^32); ключ → ближайший узел по часовой стрелке | При добавлении/удалении узла мигрирует **только ~1/N** ключей (не все) | Неравномерность без виртуальных узлов (vnodes) |

### 2.3. Consistent hashing детально

Кольцо: хэш-пространство замыкается (0 и 2^32−1 соседствуют). Каждый узел занимает точку(и) на кольце; ключ кладётся на первый узел **по часовой стрелке** от `hash(key)`.

```
       2^32-1 ─── 0
          ┌────┐
    nodeC │    │ nodeA        key K → первый узел по часовой
          │    │              стрелке от hash(K)
    nodeB └────┘
```

- **Проблема:** узлов мало → распределение сильно неравномерно (диапазоны разных размеров).
- **Решение — виртуальные узлы (vnodes):** каждый физический узел получает много точек на кольце (например 100–256 vnodes). Дисперсия нагрузки падает ~как `1/√vnodes`. Используется в Dynamo (Cassandra, Riak).
- **Главное свойство:** добавление узла затрагивает только соседний сегмент кольца → мигрирует доля ~`1/N` данных, а не все. В «чистом» `hash mod N` при смене N переезжает **почти всё**.

### 2.4. Shard key — как выбирать

Критерии хорошего ключа:
1. **Высокая кардинальность** — много различных значений (иначе данные слипаются в малое число шардов).
2. **Равномерное распределение значений** — без «тяжёлых» значений (celebrity-ключи).
3. **Мало NULL** — NULL-ключи обычно складываются в один шард.
4. **Ключ участвует в JOIN/фильтрах** — чтобы co-located join (данные с одним ключом на одном узле) был локальным, без пересылки.
5. **Стабильность** — значение не должно часто меняться (update ключа = физический перенос строки между узлами).

Анти-паттерны:
- Даты/монотонно растущие ключи при **range**-шардинге → все свежие записи идут в последний узел (hot spot).
- Низкокардинальные колонки (статус, страна из 5 значений) при hash → максимум 5 «нагруженных» шардов.
- Ключ с тяжёлым хвостом (10% значений дают 90% строк) → skew.

### 2.5. Skew и hot spot

- **Data skew (перекос данных):** на одном узле строк в разы больше, чем на остальных. Время ответа определяется **самым медленным** узлом (в Greenplum это формулируется явно: «query time is bounded by the slowest segment»).
- **Workload skew (перекос нагрузки):** данные равны, но 1% ключей получает 90% запросов (популярный товар, вирусный пост).
- Лечение:
  - сменить/составной ключ;
  - **salting** (подмешать случайный суффикс к ключу, чтобы размазать горячий ключ по узлам; читать тогда надо по всем вариантам — усложняет чтение);
  - разнести горячие ключи отдельной таблицей/кэшем;
  - для range — дробить диапазоны.

Метрика перекоса: коэффициент вариации числа строк по шардам `CV = stddev / mean` (в Greenplum — `gp_toolkit.gp_skew_coefficients`); здоровое значение близко к 0, тревожное — заметно > 0.1–0.2.

### 2.6. Rebalancing / resharding — почему это дорого

- **Перехеширование:** при изменении числа шардов `hash mod N` даёт новые номера почти для **всех** строк → полный перенос данных по сети + блокировки + риск неконсистентности.
- **Дорого — это:**
  1. Сетевой трафик (перенос доли данных, при `mod N` — почти 100%).
  2. Время недоступности или деградация (переезд идёт «живьём»).
  3. Нужна двойная бухгалтерия во время переезда (чтения из старого и нового места).
- Правильный дизайн решает это **заранее**:
  - consistent hashing → миграция ~`1/N` ключей;
  - directory-sharding → переезд одного tenant;
  - виртуальные шарды с самого начала: создай **больше логических шардов, чем узлов** (например 1024 шарда на 8 узлов = 128 на узел), и при добавлении узла переноси **целые шарды**, а не пересчитывай ключи (это делает Citus: `citus.shard_count` >> числа воркеров).

## 3. Теория репликации

### 3.1. Три модели

**1. Leader–follower (primary–replica, single-leader) — самая распространённая.**
- Все записи идут в **leader**; followers получают изменения и обслуживают чтения.
- Простая модель, легко строить read-heavy масштабирование (читать с реплик).
- Минус: все записи через один узел → потолок по записи.

```
        ┌────────┐   (sync/async)   ┌────────────┐
client ─│ Leader ├─────────────────►│ Follower 1 │  (читают)
  write └───┬────┘                  └────────────┘
            │                       ┌────────────┐
            └──────────────────────►│ Follower 2 │
                                    └────────────┘
```

**2. Multi-leader (master–master):** несколько узлов принимают записи, реплицируют друг другу.
- Плюс: пишем в ближайший ЦОД (гео), нет единой точки записи.
- Минус: **конфликты записей** (один и тот же ключ меняют в двух местах) — нужны CRDT / LWW / ручное разрешение. Применяется редко (geo-replication, офлайн-синхронизация).

**3. Leaderless (Dynamo-style, quorum):** любой узел может принять запись; запись/чтение идут сразу на несколько реплик.
- Пишем в `W` реплик, читаем с `R` реплик. Конфликты разрешаются версионированием (vector clocks) + LWW.
- Примеры: Dynamo, Cassandra, Riak, S3-стиль внутренней репликации.

### 3.2. Синхронная vs асинхронная репликация

| Свойство | Синхронная | Асинхронная |
|---|---|---|
| Запись подтверждается | Только после того, как реплика применила/получила данные | Сразу, как лидер применил локально |
| **RPO** | **= 0** (ничего не теряем) | **> 0** (теряем то, что не успело уехать за lag) |
| Латентность записи | + сетевой round-trip до реплики (1–10+ мс) | Без доп. задержки |
| Отказ реплики | **Записи блокируются** (или деградируют) — доступность падает | Лидер продолжает работать |
| Типовое применение | Финансы, критичные данные | Реплики для чтения, DR, аналитика |

**Гибриды (реальные системы почти всегда гибридны):**
- Postgres: `synchronous_standby_names` + `synchronous_commit = on | remote_write | remote_apply` — синхронно 1..N реплик, остальные async.
- Cassandra: quorum-уровень настраивается **на каждый запрос** (tunable consistency).

### 3.3. Quorum: R + W > N

Обозначения (Dynamo NWR):
- `N` — число реплик ключа (replication factor);
- `W` — сколько реплик должны подтвердить **запись**;
- `R` — сколько реплик должны ответить на **чтение**.

> **Гарантия:** если `R + W > N`, то множество читаемых реплик пересекается с множеством записанных → чтение гарантированно увидит свежую запись (при строгом quorum).

Типовые конфигурации при `N = 3`:

| W | R | Свойство |
|---|---|---|
| 2 | 2 | Баланс, переживает отказ 1 реплики (Cassandra `QUORUM`) |
| 3 | 1 | Быстрое чтение, медленная/хрупкая запись (read-heavy) |
| 1 | 3 | Быстрая запись, дорогое чтение (write-heavy) |
| 1 | 1 | Максимально быстро, но **eventual consistency** (не пересекаются) |

Оговорки:
- `R+W>N` **не равно** линеаризуемости: сloppy quorum (пишем в любые W узлов, а не «настоящие» реплики), sloppy hint, concurrent writes + LWW со сдвигом часов — всё это ломает строгую гарантию.
- Механизмы схождения (anti-entropy): **read repair** (при чтении чиним расхождения), **hinted handoff** (пока реплика лежит — пишем «с запиской» в соседний узел, потом досылаем), **Merkle trees** (фоновая сверка «холодных» ключей).

### 3.4. Консенсус: Raft / Paxos (кратко)

**Зачем нужен:** когда реплики должны **сами** выбирать нового лидера и согласовывать порядок записей, не спрашивая человека. Это основа NewSQL (Spanner/Paxos, etcd/CockroachDB/TiDB/Raft) и HA-схем БД (Patroni/etcd).

- **Raft** (понятнее, практичнее): лидер избирается большинством, все записи идут через лидера, реплицируются в лог большинству (quorum = ⌈(N+1)/2⌉ из N узлов), фиксируются после подтверждения большинства. Свойства: **safety** (никогда два лидера одновременно), **liveness** при большинстве живых.
- **Paxos** (теоретически первый, сложный): семейство протоколов, Spanner использует Paxos на каждом шарде.
- **Ключевая формула:** кластер из `N = 2f+1` узлов переживает `f` одновременных отказов. etcd обычно 3 узла → переживает 1 отказ; 5 узлов → 2 отказа.
- Где в стеке курса: **etcd** (используется Patroni, Kubernetes), **Raft в Patroni** не встроен — Patroni берёт лидерство через DCS (etcd/Consul/ZooKeeper), а уже etcd реализует Raft.

### 3.5. Модели согласованности (от сильной к слабой)

| Модель | Гарантия | Цена |
|---|---|---|
| **Linearizability (strong)** | Операции выглядят как мгновенные, в одном глобальном порядке | Медленно, недоступна при разделении |
| **Sequential** | Единый порядок операций (но не привязан к реальному времени) | Ниже |
| **Causal** | Причинно-связанные операции видны в правильном порядке | Средняя |
| **Read-your-writes** | Свои записи всегда видишь | Средняя |
| **Monotonic reads** | Не «откатываешься» назад: повторное чтение не возвращает более старые данные | Средняя |
| **Eventual** | Когда-нибудь все реплики сойдутся (при отсутствии новых записей) | Минимальная |

Практические привязки:
- Postgres sync-реплика + чтение с лидера → линейзованно.
- Чтение с async-реплики → eventual (можно прочитать устаревшее; «read-your-writes» ломается, если писать в лидера, а читать с реплики).
- S3 до 2020 → eventual; после 2020 → **strong read-after-write** (см. §5.4).
- Cassandra с `QUORUM` → «сильная eventual» (не строгая линеаризуемость).

## 4. Переход теории в инженерные расчёты (ядро лекции)

Общая логика: **от требований (объём, QPS, RPO/RTO, доступность) → к размеру узлов, числу шардов, числу реплик, сетевому бюджету и стоимости.**

### 4.1. Число шардов: по объёму данных

```
N_шардов = ⌈ total_size / size_per_shard ⌉
```

Чем ограничен `size_per_shard` (максимальный разумный размер одного шарда):
- **RAM узла:** рабочий набор шарда должен влезать в буферный кэш узла (иначе всё уходит в диск → латентность растёт на порядки). Ориентир: `working_set ≤ RAM × 0.7` (остальное — ОС, другие шарды).
- **Диск узла:** размер шарда × число реплик на узле ≤ ёмкость диска.
- **Операционные пределы:** время полного восстановления шарда (rebuild/repair) — чем больше шард, тем дольше бэкап/восстановление. Практический ориентир для Postgres-шардов: 100–500 ГБ, для Greenplum-сегмента — сотни ГБ–1 ТБ.

Пример: `total_size = 10 ТБ`, `size_per_shard = 256 ГБ` → `N = 10×1024/256 = 40` шардов.

### 4.2. Число шардов: по QPS

```
N_шардов = ⌈ QPS_total / QPS_per_shard ⌉
```

`QPS_per_shard` оценивается по ресурсам узла (см. 4.3) или по бенчмарку. Ориентиры (простые point-lookup, порядок величин):
- 1 ядро Postgres: ~500–2000 простых чтений/с (зависит от набора в памяти, индексов).
- Один узел (8–16 ядер): ~5–20 тыс. простых чтений/с.

Пример: `QPS_total = 20 000`, `QPS_per_shard = 1000` → `N = 20` шардов.

### 4.3. Число шардов: по ресурсам узла

Шард на узле потребляет 4 ресурса — считаем по каждому, берём **максимум ограничений**:

| Ресурс | Формула ограничения | Что лимитирует |
|---|---|---|
| CPU | `шардов ≤ cores × (1 / latency_с × concurrency)` | Число одновременных запросов |
| RAM | `шардов ≤ RAM / mem_per_shard_working_set` | Размер горячего набора в кэше |
| Диск (ёмкость) | `шардов ≤ disk_TB / (size_per_shard × RF / placement)` | Объём хранения |
| Диск (IOPS/пропуск) | `шардов ≤ disk_IOPS / iops_per_shard` | Интенсивность ввода-вывода |

Эвристика для баланса: число партиций в движках ≈ **2–4 × число ядер** (Spark, Trino). Это максимизирует параллелизм без излишних накладных расходов на мелкие партиции.

### 4.4. Расчёт репликации

**Replication lag (отставание реплики):**

```
lag_bytes = LSN_primary − LSN_replica   (в байтах WAL)
lag_time  ≈ lag_bytes / apply_rate      (apply_rate — скорость применения WAL на реплике)
```

- Ориентиры: в штатном режиме async streaming в Postgres — единицы–сотни мс; при burst записи или медленном диске реплики — секунды и больше.
- Чтение с реплики возвращает данные возрастом `lag_time` → это и есть **RPO чтения** и «окно потери» для записи.

**RPO (сколько данных теряем при катастрофе):**

| Режим | RPO |
|---|---|
| Синхронная репликация (`synchronous_commit=remote_apply`) | **0** |
| Асинхронная (streaming) | `write_rate × lag_time` (например 10 МБ/с × 5 с = 50 МБ) |
| S3 CRR/SRR (async, объекты) | `объекты, записанные за lag` (минуты–часы) |

**RTO (сколько времени до восстановления):**

```
RTO ≈ T_обнаружения + T_failover + T_восстановления_клиентов
```

- Patroni/etcd: `loop_wait=10с`, `ttl=30с` → обнаружение ~10–30 с, повышение реплики — секунды, клиенты переключаются (HAProxy/libpq) — секунды → **RTO ~ 30–60 с** типично.
- Greenplum mirror: переключение на mirror — минуты (зависит от числа сегментов).
- Полное восстановление узла с нуля (rebuild) — часы (зависит от объёма и сети).

**Сетевой трафик репликации:**

```
net_replication = write_rate × (RF − 1)          # полная копия, лидер рассылает всем репликам
```

Пример: `write_rate = 100 МБ/с`, `RF = 3` → лидер отдаёт `100 × 2 = 200 МБ/с` = 1.6 Гбит/с в реплики, и в сумме на дисках кластера пишется `100 × 3 = 300 МБ/с`.

**Storage amplification (размножение хранения):**

| Схема | Формула | Пример | Комментарий |
|---|---|---|---|
| Полная репликация | `RF × data` | RF=3 → 3× (overhead 200%) | Простая, быстрое восстановление |
| Erasure coding (S3/MinIO) | `(K+M)/K × data` | K=12, M=4 → 16/12 = 1.33× (overhead 33%) | Меньше места, дороже чтение/пересчёт, MinIO default EC:4 |

- MinIO: erasure set 8–16 дисков → default parity **EC:4**. На 16 дисках = 12 data + 4 parity → эффективность 75%, переживает 4 отказа дисков. Сравните: 3× репликация = 33% эффективности, переживает 2 отказа.

### 4.5. Оценка доступности

**Доступность одного узла** `a` (доля времени в работе): 99.9% → простой ~8.76 ч/год; 99.99% → ~52.6 мин/год; 99.999% → ~5.26 мин/год.

**Последовательная цепочка** (нужны ВСЕ компоненты — например, приложение → сеть → БД-шард):

```
A_serial = a₁ × a₂ × … × aₙ = aⁿ        (доступность только падает)
```

**Параллельное резервирование** (достаточно, чтобы выжил ХОТЯ БЫ один из n независимых реплик):

```
A = 1 − (1 − a)ⁿ
```

Пример: `a = 99%` (узел лежит 3.65 дня/год), `n = 3` реплики:
`A = 1 − (1−0.99)³ = 1 − 10⁻⁶ = 0.999999` = **99.9999%** (~31 с/год).

**Комбинированная оценка кластера:** кластер = `k` шардов, каждый шард — последовательное звено из `n` реплик (нужен хотя бы один живой из n):

```
A_cluster = (1 − (1−a)ⁿ)ᵏ
```

Пример: `k = 40` шардов, `n = 3`, `a = 99.9%`:
- Шард: `1 − (0.001)³ = 1 − 10⁻⁹`;
- Кластер: `(1−10⁻⁹)⁴⁰ ≈ 1 − 40×10⁻⁹ = 0.99999996` → **99.999996%**.

**Главная оговорка (обязательно говорить):** формула предполагает **независимые** отказы. В реальности отказы коррелируют: общее питание, один дата-центр/облачная AZ, общий сетевой коммутатор, общий баг в коде, общая конфигурация. Поэтому реальная доступность почти всегда **хуже** расчётной — формула даёт **верхнюю границу**. Коррелированные отказы лечатся разнесением реплик по AZ/зонам и независимостью деплоя (что в Kubernetes выражается anti-affinity + PDB).

### 4.6. Сквозной числовой пример «от N ТБ и QPS → к железу»

**Требования:**
- Логический объём: **10 ТБ** (таблица пользователей + события, hot-set 10%).
- Нагрузка: **20 000 чтений/с** (point lookups), **2 000 записей/с** (по ~3 КБ вместе с WAL).
- Требования: RPO ≤ 1 с, RTO ≤ 60 с, целевая доступность 99.99%, p99 чтения ≤ 10 мс.
- Узел (commodity): **16 vCPU, 64 ГБ RAM, 2×7.68 ТБ NVMe** (≈ 14 ТБ usable после RAID/оверхеда).

**Шаг 1 — число шардов по объёму.**
`size_per_shard = 256 ГБ` (вписывается в узел, быстрый rebuild).
`N_шардов = 10 ТБ / 256 ГБ = 39.06 → 40 шардов`.

**Шаг 2 — репликация.**
`RF = 3` (1 leader + 2 follower): RPO≈0 при sync-standby, запас на отказ 2 узлов.
Всего реплик: `40 × 3 = 120`.

**Шаг 3 — узлы по ёмкости.**
На узел кладём по 8 реплик (8 × 256 ГБ = 2 ТБ, в 14 ТБ с большим запасом под WAL/рост).
`N_узлов = 120 / 8 = 15 узлов`.

**Шаг 4 — проверка по QPS (не лимитирует).**
- Чтения: `20 000 / 120 реплик ≈ 167 чтений/с на реплику` — тривиально (узел тянет тысячи).
- Записи: `2 000 × RF=3 = 6 000 операций записи/с` на весь кластер = `400/с на узел` — комфортно.
- Вывод: **лимитирующий фактор — объём, а не CPU**. (Полезный анти-паттерн для разбора: если бы было 200 000 записей/с, лимитировала бы уже сеть/CPU.)

**Шаг 5 — память.**
Hot-set: `10 ТБ × 10% = 1 ТБ`, на 15 узлов → `~70 ГБ/узел`. При 64 ГБ RAM впритык → либо увеличить RAM до 128 ГБ, либо ужать hot-set (разделить на горячую/холодную части), либо больше узлов. **Здесь итерация:** требования к RAM поднимают число узлов до `20–24`.

**Шаг 6 — сеть репликации.**
Запись: `2 000 оп/с × 3 КБ = 6 МБ/с` первичных данных. На реплики: `6 × 2 = 12 МБ/с` = ~96 Мбит/с — смешно мало. Но при росте до `200 000 записей/с`: `200 000 × 3 КБ × 2 = 1.2 ГБ/с` = ~10 Гбит/с → нужна 10G+ сеть, и это становится **главным бюджетом**.

**Шаг 7 — доступность.**
`a = 99.9%` на узел, `n = 3` реплики: шард `1 − 10⁻⁹`, кластер 40 шардов → `≈ 99.999996%` — формально выше цели 99.99%. **Но** при коррелированных отказах (одна стойка/AZ) цифра резко падает → реплики должны быть разнесены по зонам.

**Шаг 8 — стоимость (амортизация).**
15–24 узла × ~$4 000 CAPEX / 3 года ≈ `$1 330/узел/год` → `$20 000–32 000/год` за 10 ТБ логики → `~$2 000–3 200/ТБ/год` (только железо, без сети/администрирования). Сравните с управляемым облачным хранилищем (~$20–25/ТБ/мес × 30 ТБ сырых = `$7 200–9 000/год` только за объектное хранение). Вывод: шардинг платит **администрированием и сложностью**, а не только железом.

**Итоговая таблица решения:**

| Параметр | Значение | Как получено |
|---|---|---|
| Шардов | 40 | `10 ТБ / 256 ГБ` |
| Реплик всего | 120 | `40 × RF(3)` |
| Узлов | 15 (20–24 с учётом RAM) | `120 / 8` и проверка hot-set |
| Сеть репликации | ~12 МБ/с (96 Мбит/с) | `write_rate × (RF−1)` |
| RPO | ≈0 (sync standby) | `synchronous_commit` |
| RTO | 30–60 с | Patroni: `loop_wait 10с + ttl 30с + promote` |
| Доступность (расчёт) | 99.999996% | `(1−(1−a)³)⁴⁰` |

## 5. Примеры на стеке курса

### 5.1. Kafka — партиции как эталонный пример шардинга

- Топик = набор **партиций**; партиция — append-only лог на диске. Число партиций = верхняя граница параллелизма потребителей в группе.
- Ключ сообщения → партиция по **murmur2 hash** (стандартный partitioner): `partition = hash(key) % num_partitions` — это классический hash-sharding.
- **Свойства:** внутри партиции — строгий порядок; порядок между партициями не гарантирован. Увеличение числа партиций **не перераспределяет** существующие сообщения (в отличие от `hash mod N` в БД) — новые сообщения просто идут в новые партиции.
- Репликация: каждая партиция имеет leader + followers (ISR), записи идут через leader, чтение — тоже (по умолчанию), консенсус лидера — через ZooKeeper/KRaft (Raft).
- Вывод: Kafka — «чистый» случай, где **шардирование (партиции) и репликация (ISR) видны явно** и независимы.

### 5.2. Greenplum (MPP, shared-nothing)

**Архитектура:** master (coordinator) + N **сегментов** (segment hosts), каждый сегмент — свой Postgres-процесс и своё хранилище.

```
        ┌────────────┐
 client─│  Master    │  планирует запрос, собирает результат (Gather)
        └─────┬──────┘
   ┌──────────┼──────────┐
   ▼          ▼          ▼
Segment 1  Segment 2  ... Segment N     (у каждого — свой набор строк)
   │          │          │
 Mirror 1   Mirror 2   Mirror N         (физическая реплика primary-сегмента)
```

**Шардирование — distribution policy (ключ распределения):**
- `DISTRIBUTED BY (col)` — **hash** распределение по ключу; строки с одинаковым ключом попадают на один сегмент → **co-located join** без пересылки.
- `DISTRIBUTED RANDOMLY` — round-robin (по умолчанию, если ключ не указан); подходит когда нет хорошего ключа, но ломает co-located join.
- `DISTRIBUTED REPLICATED` — таблица копируется на все сегменты (для маленьких справочников — аналог broadcast join).
- Правило выбора ключа: высокая кардинальность, равномерность, минимум NULL, участие в JOIN.

**Репликация — segment mirror:**
- Каждый primary-сегмент имеет mirror (обычно на другом хосте); при отказе primary mirror автоматически повышается, `gpstate`/`gprecoverseg` восстанавливают. Это **синхронная** защита (данные не теряются при отказе сегмента).

**Движение данных (Motion):** если ключ JOIN не совпадает с ключом распределения, в плане появляются **Redistribute Motion** (пересылка) / **Broadcast Motion** / **Gather Motion** — это и есть цена «неправильного» шардирования, видимая в `EXPLAIN`.

**Диагностика skew:**
- Псевдо-SQL: `SELECT gp_segment_id, count(*) FROM t GROUP BY 1;` — строки по сегментам должны быть примерно равны.
- `gp_toolkit.gp_skew_coefficients` (коэффициент вариации) и `gp_toolkit.gp_skew_idle_fractions` (простой сегментов при сканах; >10% — сигнал к пересмотру ключа).

**Партиционирование vs распределение (не путать):** партиции (по дате) режут таблицу **внутри сегмента** для pruning сканов; распределение разносит строки **между** сегментами. Это два ортогональных измерения.

### 5.3. Postgres: партиции, logical replication, Citus, Patroni

**Нативные партиции (логическое шардирование на одном сервере):**
- `PARTITION BY RANGE / LIST / HASH` (PG 10–11+). Запрос с условием по ключу партиционирования → **partition pruning**: читаются только нужные партиции.
- Дерево партиций — `pg_partition_tree()`, размеры — по `pg_class`/`relpages`.
- Это «шардинг без распределения»: один сервер, но те же паттерны (выбор ключа, skew, hot partition).

**Физическая streaming-репликация:**
- `wal_level=replica`, `hot_standby=on`, реплика получает WAL от лидера и применяет (`pg_stat_replication`, `replay_lsn`).
- `synchronous_standby_names` + `synchronous_commit` (`off/local/remote_write/on/remote_apply`) — настройка RPO от «теряем» до «0».
- Lag = разница `sent_lsn`/`write_lsn`/`replay_lsn` — прямое измерение §4.4.

**Logical replication (выборочная, таблицы):**
- `CREATE PUBLICATION` (лидер) / `CREATE SUBSCRIPTION` (подписчик); реплицируются **отдельные таблицы**, поддерживается фильтрация строк (PG15+) и cross-version.
- Не реплицирует DDL; для UPDATE нужен PK или `REPLICA IDENTITY FULL`.
- Применение: CDC, выгрузка в аналитику, миграции с нулевым даунтаймом.

**Citus (шардинг Postgres поверх PG):**
- Кластер: **coordinator** + **worker**-узлы. Таблица распределяется: `create_distributed_table(t, 'dist_col')`.
- Число шардов: **`citus.shard_count`** (default **32**), репликация: **`citus.shard_replication_factor`** (default **2**).
- Важно: шардов (32) обычно **больше**, чем воркеров → при добавлении воркера переносятся **целые шарды** (`citus_rebalance_start()`), а не пересчитывается `hash mod N` — это и есть «заранее созданные виртуальные шарды».
- **Co-location:** таблицы с одинаковым типом ключа, числом шардов и replication factor попадают на одни узлы → локальные JOIN без пересылки.
- **Reference tables** (маленькие справочники) реплицируются на все воркеры — аналог `DISTRIBUTED REPLICATED` и broadcast join.
- Метаданные: `pg_dist_shard`, `pg_dist_placement`, вьюха `citus_shards`.

**Patroni + etcd (HA, лидер-элекция):**
- Patroni — Python-демон на каждом узле PG; **DCS** (etcd/Consul/ZooKeeper) хранит состояние и **leader-ключ**.
- Лидерство: узлы соревнуются за ключ `/service/<scope>/leader`; лидер обновляет lease (`loop_wait=10с`, `ttl=30с`). Не продлил → ключ истёк → выборы среди standby; побеждает узел с **наибольшим LSN** (минимум потерь).
- **etcd сам реализует Raft** (3 узла → переживает 1 отказ) — поэтому split-brain исключён: лидер ровно один.
- `patronictl` — `list`, `switchover`, `failover`; `pg_rewind` возвращает отставший узел в строй.
- RPO/RTO: sync-standby → RPO=0; RTO = обнаружение (10–30 с) + promote + переподключение клиентов.

### 5.4. Spark: партиции, repartition/coalesce, skew

- **Партиции RDD/DataFrame** = единицы параллелизма (одна партиция — одна задача на executor). Данные уже «шардированы» по партициям в памяти/на диске.
- **`repartition(n)`** — полный **shuffle** (hash-переразложение по новому ключу/round-robin), выравнивает распределение, но дорого (сеть+диск).
- **`coalesce(n)`** — **слияние** партиций **без полного shuffle** (только уменьшение числа, перемещаются соседние данные); не лечит skew.
- **Число shuffle-партиций:** `spark.sql.shuffle.partitions` (default **200**) — ключевой параметр для join/aggregation; эвристика: `2–4 × суммарное число ядер` и `размер партиции ~128 МБ`.
- **Data skew в join:** один ключ (например `user_id=null` или «горячий» id) собирает почти все строки в одну партицию → одна задача тащит всё. Лечение:
  - **salting** — добавить к ключу случайный суффикс `0..k-1`, размазать, потом собрать;
  - **broadcast join** для маленькой таблицы (`spark.sql.autoBroadcastJoinThreshold`, default **10 МБ**) — маленькая таблица копируется на все executors, shuffle не нужен;
  - **AQE** (Adaptive Query Execution, Spark 3+): `spark.sql.adaptive.enabled=true` — динамическое слияние партиций после shuffle и **skew join optimization** (`spark.sql.adaptive.skewJoin.enabled`).
- **Связь с теорией:** выбор partition key = выбор shard key; skew в Spark = тот же skew, что в Greenplum/Citus, только на уровне задач, а не узлов.

### 5.5. S3 / MinIO: репликация объектов и согласованность

- S3 — **объектное хранилище**, «шардирование спрятано внутри» (ключи объектов автоматически распределяются по инфраструктуре). Наружу торчат **репликация и согласованность**.
- **Репликация объектов (async):**
  - **SRR** (Same-Region Replication) — в другой бакет того же региона (DR внутри региона, копии для теста).
  - **CRR** (Cross-Region Replication) — в другой регион (DR, комплаенс, гео-латентность).
  - **S3 Replication Time Control (S3 RTC):** предсказуемое время — **99.99% новых объектов реплицируются за 15 минут** (SLA: 99.9% за 15 мин в месяц). Без RTC — «обычно минуты, крупные объекты — часы», SLA нет.
  - Реплицируются **только новые** объекты; старые — через S3 Batch Replication.
- **Согласованность (важный факт):** с **декабря 2020** S3 даёт **strong read-after-write consistency** для PUT/DELETE/GET/LIST (и метаданных/ACL) во всех регионах **бесплатно**. До этого был eventual → требовались костыли (EMRFS Consistent View, S3Guard) — теперь не нужны.
- **MinIO:** вместо полной репликации — **erasure coding**: default **EC:4** (8–16 дисков). На 16 дисках = `12 data + 4 parity` → эффективность 75%, переживает 4 отказа диска. Quorum записи: при `M < N/2` — `K`, при `M = N/2` (4+4) — `K+1` (защита от split-brain). Это прямой пример «replication vs erasure coding» из §4.4.

### 5.6. Iceberg: hidden partitioning, partition evolution

- **Hidden partitioning (скрытое партиционирование):** пользователь не создаёт колонку-партицию; партиции вычисляются **из существующих колонок через transform**.
  - Transforms: `identity`, `bucket[N]` (hash + mod N), `truncate[W]`, `year/month/day/hour` (от timestamp), `void`.
  - Запросы пишутся по исходной колонке: `WHERE event_time > ...` — а Iceberg сам делает pruning по производным партициям. Физическая раскладка **скрыта** от пользователя.
- **Partition evolution (эволюция партиций):** изменение партиционирования — **metadata-only**, без переписывания файлов данных.
  - `ALTER TABLE t ADD/DROP/REPLACE PARTITION FIELD ...` создаёт новый **partition spec** (со своим id); старые файлы хранят свой spec-id, новые пишутся по новому spec; планировщик запроса обрабатывает смешанные spec'и (split planning).
  - Это решает главную боль «классического» партиционирования (Hive): там смена партиций = **полное переписывание данных**.
- **Практика:** начинать грубо (day), эволюционировать мельче (hour) при росте; для высококардинальных колонок — `bucket(N, col)` с N=16–64 (аналог hash-sharding внутри таблицы); избегать сверхмелких партиций (small-file sprawl).
- **Sort order** — упорядочивание данных при записи (аналог кластеризации) для эффективного сжатия и сканов.

### 5.7. Trino: hash partitioning в join/aggregation

- Trino — распределённый SQL-движок поверх шардированных данных (Iceberg/S3): coordinator + workers, запрос = дерево **stages**, между ними — **exchange** (пересылка данных между воркерами).
- **JOIN (partitioned hash join):** обе стороны переразлагаются **по ключу join (hash)** между воркерами — временный «reshard на лету»; каждая пара строк с одним ключом встречается на одном воркере.
- **Broadcast join:** маленькая правая сторона целиком рассылается на все воркеры (аналог `DISTRIBUTED REPLICATED`, reference tables, broadcast в Spark) — shuffle левой стороны не нужен.
- **Aggregation:** двухфазный hash aggregation — partial (локально на воркере) → пересылка **по grouping key** → final.
- **Параллелизм:** число **splits** (куски данных, которые отдаёт коннектор, напр. файлы/партиции Iceberg) → задачи → потоки. Размер split'а и число воркеров = те же «партиции и ядра» из §4.3.
- **Смысл для лекции:** Trino не хранит данные — он **перешардирует их на лету** по hash-ключу; стоимость этой операции — сетевой exchange, и её можно увидеть в плане запроса (это аналог Motion в Greenplum).

### 5.8. Kubernetes: replicas, StatefulSet, PDB

- **ReplicaSet / Deployment `replicas`** — репликация **приложения** (stateless): `replicas: 3` держит 3 экземпляра; controller loop сверяет желаемое/фактическое — это «replica repair» как в репликации БД.
- **StatefulSet** — для БД/шардов: **стабильные имена** (`pod-0`, `pod-1`, …), стабильные PVC (диск привязан к pod), порядок при старте/остановке. Нужен, когда экземпляр = конкретный шард со своим диском (Citus worker, Greenplum-сегмент, Kafka-брокер).
- **PodDisruptionBudget (PDB)** — ограничение **добровольных** вытеснений (drain узла, обновления): `minAvailable: 2` при 3 репликах → нельзя выселить 2 сразу → в кластере всегда жив quorum. Аналог «не убивай больше f узлов» из §3.4.
- **Anti-affinity / topology spread** — разнесение реплик по **разным узлам/AZ** (иначе «3 реплики» на одной машине = одна точка отказа). Это операционная реализация «независимости отказов» из §4.5.
- **Связь с темой:** Kubernetes не знает про «шарды данных», но даёт примитивы, из которых шардированная БД собирается: StatefulSet = идентичность шарда, PDB = защита quorum, anti-affinity = независимость реплик.

## 6. Практика (словесный docker-сценарий, без исполняемого кода)

Цель — **пощупать** все числа из §4: распределение строк по шардам, replication lag, время failover.

### 6.1. Сценарий A: Postgres + Citus (шардирование «вживую»)

**Что поднять:** docker-compose с **одним coordinator** и **двумя-тремя worker**-узлами (образ Citus, на базе Postgres). Coordinator хранит метаданные, worker'ы — шарды.

**Что сделать и увидеть:**
1. Создать распределённую таблицу: `create_distributed_table(events, 'user_id')`; проверить, что `citus.shard_count` (например 32) больше числа воркеров — шарды легли на воркеры.
2. Посмотреть метаданные: вьюха `citus_shards` / таблицы `pg_dist_shard`, `pg_dist_placement` — какой шард на каком воркере.
3. Наполнить таблицу данными и **измерить распределение**: на каждом воркере подсчитать число строк в шардах → построить min/max/mean и коэффициент вариации (skew). Убедиться, что hash-ключ с высокой кардинальностью даёт ровное распределение.
4. Повторить с **плохим ключом** (низкокардинальная колонка, например «страна» из 5 значений) → увидеть skew: почти все строки в малом числе шардов.
5. `EXPLAIN` запроса с JOIN по ключу распределения → убедиться, что пересылки между воркерами нет (co-located join), и с JOIN по другому ключу → появляется repartition.
6. С `citus.shard_replication_factor = 2` «уронить» один worker (docker stop) → чтение продолжается с реплик шардов; запустить `citus_rebalance_start()` после добавления нового воркера → увидеть перенос **целых шардов**, а не пересчёт всех ключей.

### 6.2. Сценарий B: Patroni + etcd (репликация и failover)

**Что поднять:** 3 узла PostgreSQL с Patroni + 3 узла etcd (etcd-кластер Raft, нечётное число).

**Что сделать и измерить:**
1. `patronictl list` — увидеть primary и standby, их LSN-позиции.
2. **Replication lag:** на primary выполнить `pg_stat_replication` → разница `sent/write/replay_lsn` → перевести в байты/секунды; включить нагрузку записями и увидеть рост lag; сравнить `synchronous_commit = on` (lag≈0, но латентность записи выросла) и `off`.
3. **Failover (RTO):** `docker stop` на primary → засечь время: истечение lease в etcd (`ttl=30с`) → выборы → повышение standby с наибольшим LSN → клиенты переподключаются. Измерить **RTO** (ожидаемо 30–60 с) и убедиться, что **RPO=0** (sync-standby): потерянных транзакций нет.
4. Включить обратно упавший узел → `pg_rewind` догоняет его, он становится standby.

### 6.3. Сценарий C: Greenplum или Postgres-партиционирование (облегчённый вариант)

- **Если есть ресурсы:** Greenplum в docker — создать таблицу с `DISTRIBUTED BY`, `SELECT gp_segment_id, count(*) ... GROUP BY 1` → строки по сегментам; `gp_toolkit.gp_skew_coefficients` → коэффициент перекоса; сравнить hash/random/replicated.
- **Облегчённый вариант (Postgres нативные партиции):** `PARTITION BY RANGE/HASH`, `pg_partition_tree()`; `EXPLAIN` с условием по ключу партиционирования → partition pruning (читаются не все партиции); измерить число строк по партициям — skew при неудачном разбиении (например одна «горячая» партиция по дате).

### 6.4. Сценарий D: Spark local (партиции и skew)

**Что поднять:** Spark в local-режиме (одна JVM, мастер `local[*]`).

**Что сделать и измерить:**
1. Создать DataFrame, `repartition(8)` → `rdd.getNumPartitions()`; распределить строки и через `glom()` посмотреть число строк по партициям.
2. Сравнить `repartition` (полный shuffle) и `coalesce` (без shuffle) — засечь время и увидеть, что coalesce не выравнивает skew.
3. Создать **skew-ключ** (например один `user_id` с 90% строк) → join → увидеть одну гигантскую партицию; применить **salting** (ключ + случайный суффикс) → партиции выровнялись.
4. Поиграть `spark.sql.shuffle.partitions` (default 200) при малом числе ядер → увидеть много мелких партиций → уменьшить до `2–4 × ядра`.
5. Broadcast join: маленькая таблица < 10 МБ → план без shuffle (broadcast exchange).

### 6.5. Что измерять (сводная таблица метрик)

| Метрика | Где смотреть | Связь с теорией |

## 7. Вопросы студентам

### Расчётные

1. **Дано:** 20 ТБ данных, RF=3, узел 8 ТБ usable. Сколько минимум узлов только под ёмкость? (Ответ: 20×3/8 = 7.5 → **8 узлов**; не забыть оверхед WAL/рост.)
2. **Дано:** 50 000 чтений/с, один узел тянет 5 000 чтений/с. Сколько шардов нужно по QPS? (Ответ: 10.) Если RF=3 и читать с реплик — как изменится расчёт? (Ответ: реплики тоже обслуживают чтение → нужно ~4 шарда по 3 реплики.)
3. **Дано:** write_rate = 50 МБ/с, RF=4. Какой сетевой трафик генерит лидер на репликацию и сколько суммарно пишется на диски? (Ответ: 150 МБ/с на реплики, 200 МБ/с суммарно.)
4. **Дано:** узел доступен на 99% времени, у нас 2 реплики. Какова доступность «хотя бы один жив»? А 3 реплики? (Ответ: 1−0.01²=99.99%; 1−0.01³=99.9999%.) Почему реальная доступность будет хуже? (Коррелированные отказы.)
5. **Дано:** N=3, W=2. Какое минимальное R гарантирует, что чтение увидит свежую запись? (Ответ: R>1, т.е. R=2.) Что произойдёт при R=1, W=1? (Eventual consistency.)
6. **Дано:** RPO ≤ 1 с при write_rate 20 МБ/с и async-репликации. Какой максимальный lag допустим? (Ответ: lag ≤ 1 с → за это время уйдёт ≤ 20 МБ.)

### Концептуальные

7. Почему **range**-шардинг по времени/монотонному ключу даёт hot spot, и как его лечить? (Ответ: свежие записи идут в последний диапазон; лечение — hash по вторичному ключу, сальтинг, дробление диапазонов, directory-шардинг.)
8. Sync vs async репликация: что платим за RPO=0? (Ответ: латентность записи = сетевой round-trip, и блокировка записей при недоступной реплике → снижение доступности.)
9. Когда **не нужно** шардирование? (Ответ: данные влезают в один узел по объёму/QPS; затраты на распределённость (сеть, координация, администрирование) превышают выгоду; workload — OLTP с сильными транзакциями, где cross-shard транзакции дороги.)
10. Почему resharding дорог, и как дизайн заранее снижает эту цену? (Ответ: `hash mod N` перекладывает почти все ключи; consistent hashing / directory / «больше виртуальных шардов, чем узлов» ограничивают перенос долей ~1/N или целыми шардами.)
11. Как Iceberg «прячет» партиционирование и почему эволюция партиций ничего не переписывает? (Ответ: партиции вычисляются transform'ом из колонок, в схеме нет партиционной колонки; смена spec — metadata-only, старые файлы хранят свой spec-id, планировщик читает смешанные spec'и.)
12. Что означает «query time is bounded by the slowest segment» в Greenplum и как это связано с выбором distribution key? (Ответ: skew → один сегмент обрабатывает больше строк → он и определяет время запроса; равномерный ключ минимизирует максимум.)
13. Почему S3 после 2020 не нужен S3Guard/EMRFS Consistent View? (Ответ: strong read-after-write consistency для PUT/DELETE/GET/LIST стала встроенной.)
14. Raft: сколько узлов нужно, чтобы пережить 2 одновременных отказа? (Ответ: N=2f+1 → f=2 → 5 узлов.) Почему etcd ставят нечётным числом?

## Приложение: карманная шпаргалка формул

```
Число шардов:        N = ⌈ total_size / size_per_shard ⌉  (и по QPS, и по ресурсам — берём max)
Репликация:          net = write_rate × (RF − 1)
Storage amplification:  полная копия = RF×;  erasure coding = (K+M)/K ×
Quorum:              R + W > N  → чтение видит свежую запись
Lag:                 lag_time ≈ lag_bytes / apply_rate
RTO:                 RTO ≈ T_обнаружения + T_failover + T_клиентов
Доступность (параллель):  A = 1 − (1 − a)ⁿ
Доступность кластера:     A_cluster = (1 − (1−a)ⁿ)ᵏ
Консенсус:           N = 2f + 1  →  переживает f отказов
Партиции:            ~2–4 × число ядер;  размер партиции ~128 МБ (Spark)
```
