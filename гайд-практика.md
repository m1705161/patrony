# Практика: шардирование и репликация — пошаговый гайд

Стек: **Citus** (шардированный Postgres) и **Patroni + etcd** (отказоустойчивый Postgres).

Ты пройдёшь по шагам своими руками и «пощупаешь» обе вещи, о которых лекция:
- часть A — **шардирование**: руками разрежешь таблицу по ключу и увидишь, как строки разъехались по узлам;
- часть B — **репликация и failover**: убьёшь главный узел и замеришь, за сколько поднимется новый.

Всё на Docker. Часть A проверена на официальном образе Citus. Часть B использует официальный docker-compose из репозитория Patroni.

---

## 0. Что мы строим

```
                 ┌──────────────┐
  ты пишешь SQL → │ coordinator  │   (Citus)
                 └──────┬───────┘
           ┌────────────┼────────────┐
           ▼            ▼            ▼
       ┌────────┐  ┌────────┐  ┌────────┐
       │ worker │  │ worker │  │ worker │    ← куски таблицы
       └────────┘  └────────┘  └────────┘

                 ┌──────────────┐
                 │     etcd     │  ← «кто сейчас главный» (Raft)
                 └──────┬───────┘
           ┌────────────┴────────────┐
           ▼                         ▼
     ┌──────────┐             ┌──────────┐
     │ primary  │──разметка──→│ standby  │   (Patroni)
     └──────────┘             └──────────┘
```

Часть A и B независимы — можно делать в любом порядке, или только одну.

# Часть A. Citus — шардирование своими руками

## A1. Поднимаем кластер

Создай рабочую папку и положи в неё `docker-compose.yml`:

```bash
mkdir -p ~/sharding && cd ~/sharding
```

Файл `docker-compose.yml`:

```yaml
version: '3'

services:
  master:
    container_name: "${COMPOSE_PROJECT_NAME:-citus}_master"
    image: 'citusdata/citus:12.1'
    ports: ["${COORDINATOR_EXTERNAL_PORT:-5432}:5432"]
    labels: ['com.citusdata.role=Master']
    environment: &AUTH
      POSTGRES_USER: "${POSTGRES_USER:-postgres}"
      POSTGRES_PASSWORD: "${POSTGRES_PASSWORD:-postgres}"
      PGUSER: "${POSTGRES_USER:-postgres}"
      PGPASSWORD: "${POSTGRES_PASSWORD:-postgres}"
      POSTGRES_HOST_AUTH_METHOD: "${POSTGRES_HOST_AUTH_METHOD:-trust}"

  worker:
    image: 'citusdata/citus:12.1'
    labels: ['com.citusdata.role=Worker']
    depends_on: [master]
    environment: *AUTH
```

> Здесь `master` — это **coordinator** (узел, куда ты пишешь SQL), а `worker` — узел-хранитель кусков. Официальный compose называет координатора «master» — не путай с репликацией: здесь мастер = координатор, а не «главная копия».

Запускаем:

```bash
docker compose up -d
```

Проверка, что оба контейнера поднялись:

```bash
docker ps
```

Должны быть `citus_master` и `citus_worker`.

## A2. Регистрируем воркер у координатора

Сначала координатор говорит сам себе «я координатор», потом добавляет воркер:

```bash
docker compose exec master psql -U postgres -c "SELECT citus_set_coordinator_host('citus_master', 5432);"
docker compose exec master psql -U postgres -c "SELECT citus_add_node('citus_worker', 5432);"
```

Проверка, что воркер подключился:

```bash
docker compose exec master psql -U postgres -c "SELECT * FROM master_get_active_worker_nodes();"
```

Должно вывести строку про `citus_worker` с портом `5432`.

## A3. Создаём распределённую таблицу

Зайди в psql координатора:

```bash
docker compose exec master psql -U postgres
```

Внутри выполняй по очереди:

```sql
-- обычная таблица, как всегда
CREATE TABLE events (
    user_id bigint,
    payload text
);

-- магия: говорим Citus резать таблицу по user_id
SELECT create_distributed_table('events', 'user_id');
```

Теперь таблица распределённая. При создании Citus нарезал на неё **32 шарда** (это значение по умолчанию `citus.shard_count`), хотя физических воркеров у нас один. Посмотрим:

```sql
SELECT shard_count FROM citus_tables WHERE table_name = 'events'::regclass;
```

Выведет `32` — кусков больше, чем машин. Именно поэтому при добавлении нового воркера Citus переедет **целыми кусками**, а не станет пересчитывать все строки заново.

## A4. Заливаем данные и смотрим распределение

Наполним таблицу миллионом строк через `generate_series` (не нужно качать датасеты):

```sql
INSERT INTO events SELECT i, 'event-' || i FROM generate_series(1, 1000000) AS i;
```

Теперь посмотрим, как куски легли на воркер. У нас один воркер, поэтому все 32 шарда на нём — но зато видно размеры кусков:

```sql
SELECT shardid, shard_size, nodename FROM citus_shards
WHERE table_name = 'events'::regclass;
```

> Колонка называется `shard_size` (не `size`) — это актуальное имя в Citus 12.x.

Дальше самое интересное — **сколько строк в каждом шарде**. Для этого зайдём на сам воркер. Выходи из psql (`\q`) и выполни на воркере.

> ⚠️ Важно (Citus 12.x): по умолчанию шарды на воркере **скрыты** из системных таблиц (`pg_stat_user_tables`, `pg_class`) из-за настройки `citus.override_table_visibility = on`. Поэтому просто `SELECT ... FROM pg_stat_user_tables WHERE relname LIKE 'events_%'` вернёт **пусто**, хотя данные на месте. Сначала выключи скрытие в этой сессии:

```bash
docker compose exec worker psql -U postgres -c \
  "SET citus.override_table_visibility = off;
   SELECT relname, n_live_tup FROM pg_stat_user_tables WHERE relname LIKE 'events_%' ORDER BY n_live_tup DESC LIMIT 40;"
```

> `events_<id>` — это и есть физические шарды на воркере. `n_live_tup` — примерное число строк в каждой. Должны быть примерно равны по ~1 000 000 ÷ 32 ≈ 31 000 строк на шард. Равномерность = хороший ключ.

## A5. Ломаем распределение плохим ключом

Теперь покажем, что выбор ключа — это и есть вся соль. Создадим таблицу с **низкокардинальным** ключом (мало разных значений) и увидим перекос:

```sql
CREATE TABLE bad (
    country text,
    v int
);
SELECT create_distributed_table('bad', 'country');

INSERT INTO bad
SELECT country, 1
FROM (VALUES ('ru'), ('us'), ('de'), ('fr'), ('in')) AS c(country),
     generate_series(1, 200000);
```

Здесь всего 5 разных стран, а `hash(country) mod 32` даст всего **5 нагруженных шардов** из 32 — остальные пустые. Проверь на воркере:

```bash
docker compose exec worker psql -U postgres -c \
  "SET citus.override_table_visibility = off;
   SELECT relname, n_live_tup FROM pg_stat_user_tables WHERE relname LIKE 'bad_%' ORDER BY n_live_tup DESC;"
```

Наглядно видно: пара шардов с сотнями тысяч строк, а почти все — с нулём. Это тот самый **skew / hot spot** из лекции.

## A6. Co-located join — ради чего всё это

Последний акцент: если таблицы бьются по **одному и тому же** ключу, их JOIN происходит локально, без пересылки между узлами. Посмотрим план:

```sql
CREATE TABLE users (user_id bigint, name text);
SELECT create_distributed_table('users', 'user_id');
INSERT INTO users SELECT i, 'user-' || i FROM generate_series(1, 1000000) AS i;

EXPLAIN (COSTS OFF)
SELECT * FROM events JOIN users USING (user_id);
```

В плане **не должно** быть узла с перераспределением данных между воркерами (в Citus оно называется `Distributed Subplan` / пересылка через задачу `... reference` ). Если оба ключа совпали — JOIN локальный и дешёвый.

# Часть B. Patroni + etcd — репликация и failover

## B1. Берём готовый compose из репозитория Patroni

Официальный репозиторий Patroni содержит готовый `docker-compose.yml` (Patroni + etcd + haproxy). Клонируем и запускаем:

```bash
git clone --depth 1 https://github.com/zalando/patroni.git ~/patroni
cd ~/patroni
```

> ⚠️ В актуальной версии репозитория `docker-compose.yml` лежит в **корне** репо (`~/patroni/docker-compose.yml`), **не** в `docker/`. Каталог `docker/` теперь содержит только `README.md`, `entrypoint.sh` и `patroni.env`.

Сначала соберём образ (займёт несколько минут — ставит Python, Patroni, etcd, haproxy):

```bash
docker build -t patroni .
```

Затем запускаем кластер:

```bash
docker compose up -d
```

> В актуальном compose **3 узла** Patroni (`patroni1/2/3`) + **3 etcd** + haproxy (в старых версиях было 2 Patroni). Имена контейнеров: `demo-patroni1`, `demo-etcd1`, `demo-haproxy` и т.д.

Подожди, пока поднимутся контейнеры (Patroni инициализирует новый primary, ~10–15 с), и посмотри их имена:

```bash
docker ps
```

Нужны минимум: три контейнера Patroni и etcd. Дальше подставляй реальные имена (в примерах — `demo-patroni1` … `demo-patroni3`).

## B2. Смотрим, кто главный

`patronictl list` показывает кластер, кто leader, кто replica:

```bash
docker exec demo-patroni1 patronictl list
```

Вывод примерно такой:

```
+ Cluster: demo (…) ----+----+-------------+-----+------------+-----+
| Member   | Host       | Role    | State     | TL | Receive LSN | Lag |
+----------+------------+---------+-----------+----+-------------+-----+
| patroni1 | 172.20.0.5 | Leader  | running   |  1 |             |     |
| patroni2 | 172.20.0.4 | Replica | streaming |  1 |   0/4000060 |   0 |
| patroni3 | 172.20.0.2 | Replica | streaming |  1 |   0/4000060 |   0 |
+----------+------------+---------+-----------+----+-------------+-----+
```

## B3. Смотрим репликацию: запись видна на standby

Самый наглядный способ убедиться, что репликация работает — записать строку на лидере и прочитать её на репликах. Запиши на лидере (подставь имя текущего Leader):

```bash
docker exec demo-patroni3 psql -U postgres -c \
  "CREATE TABLE replicacheck (id serial primary key, t text default now()::text);
   INSERT INTO replicacheck (t) VALUES (now()::text);"
```

Прочитай на репликах:

```bash
docker exec demo-patroni1 psql -U postgres -c "SELECT * FROM replicacheck;"
docker exec demo-patroni2 psql -U postgres -c "SELECT * FROM replicacheck;"
```

Строка должна быть видна на **обеих** репликах (тот же `id`, тот же `t`) — это и есть репликация: пишешь в один Postgres, а данные доступны во всех.

## B4. Смотрим replication lag

Replication lag — насколько standby отстал от primary. Видно на primary:

```bash
docker exec demo-patroni3 psql -U postgres -c \
  "SELECT usename, application_name, state, sync_state,
          pg_wal_lsn_diff(sent_lsn, replay_lsn) AS lag_bytes
   FROM pg_stat_replication;"
```

`lag_bytes` — сколько байт journal ещё не доехало до standby. В спокойном режиме это 0 или единицы байт.

## B5. Failover: убиваем primary и засекаем время

Это кульминация. Узнай, кто сейчас **Leader** (из `patronictl list`, пусть будет `patroni3`), и «урони» его:

```bash
docker stop demo-patroni3
```

Прямо сейчас запусти секундомер (телефон), и смотри на оставшемся узле:

```bash
docker exec demo-patroni1 patronictl list
```

Повторяй раз в пару секунд. Ты увидишь, как очередной standby становится `Leader`.

> ⚠️ `docker stop` шлёт SIGTERM — Patroni успевает сделать **graceful** shutdown (лидер явно запишет `stopped` в etcd), поэтому выборы проходят за **несколько секунд** (в нашем прогоне ~5 с). Если нужен «аварийный» сценарий из лекции (узел молча упал, ждём истечения lease `ttl=30`), используй `docker kill` (SIGKILL) — тогда RTO будет 30–60 с. Опробуй оба и заметь разницу: время обнаружения зависит от `loop_wait` + `ttl` в конфиге Patroni (`patronictl show-config`).

## B6. Возвращаем упавший узел в строй

Когда хочешь вернуть упавший узел (он должен стать standby, а не новым лидером):

```bash
docker start demo-patroni3
docker exec demo-patroni1 patronictl list
```

Упавший узел догонит журнал (обычно через `pg_rewind`, если отстал несогласованно) и встанет в строй как `Replica`. Потерь нет.

## 2. Остановить и удалить (когда закончил)

```bash
# Citus
cd ~/sharding && docker compose down

# Patroni
cd ~/patroni && docker compose down
```

Полная очистка (с удалением данных и образов):

```bash
cd ~/sharding && docker compose down -v
cd ~/patroni && docker compose down -v
docker image rm citusdata/citus:12.1
docker image rm patroni
```

> Если контейнеры поднимались **не** через compose в этих папках (например, руками через `docker run`, или под другими именами — `citus_coordinator`, `citus_worker`, `demo-patroni1/2/3`, `demo-etcd1/2/3`, `demo-haproxy`), удали их по одному: `docker rm -f <имя>`, затем сети (`docker network ls` → `docker network rm patroni_demo`) и папки-клоны (`rm -rf ~/sharding ~/patroni`).

Полный след после лабы, который нужно убрать:
- контейнеры: `citus_coordinator`, `citus_worker`, `demo-patroni1/2/3`, `demo-etcd1/2/3`, `demo-haproxy`;
- сети: `patroni_demo`, `sharding_default`;
- образы: `citusdata/citus:12.1`, `patroni` (и неиспользуемый `postgres:17`);
- папки: `~/sharding`, `~/patroni`.

## 3. Если что-то пошло не так

| Симптом | Причина | Что сделать |
|---|---|---|
| `citus_add_node` падает с ошибкой | воркер ещё не поднялся или имя не то | подожди 5 с, проверь `docker ps`, повтори |
| `master_get_active_worker_nodes` пусто | забыл `citus_set_coordinator_host` или `citus_add_node` | выполни обе команды из A2 по порядку |
| в `citus_shards` куски пустые | INSERT был в не-распределённую таблицу | проверь, что вызвал `create_distributed_table` до вставки |
| порт 5432 занят | что-то уже слушает на 5432 | в compose задай `COORDINATOR_EXTERNAL_PORT=5435` (переменная окружения): `COORDINATOR_EXTERNAL_PORT=5435 docker compose up -d`, и подключайся на 5435 |
| Patroni: `docker compose up -d` долго собирает | первый билд образа из Dockerfile | подожди — это разово; дальше стартует быстро |
| Patroni: нет контейнера `demo-patroni1` | в новой версии compose имена другие | смотри реальные имена через `docker ps` и подставляй их |
| `patronictl` не найден | выполнил не в контейнере | запускай всегда через `docker exec <контейнер> patronictl` |
| failover не происходит | etcd не поднялся, или нет quorum | проверь `docker ps`, что etcd есть и жив; логи: `docker logs demo-etcd1` |
| на воркере пусто в `pg_stat_user_tables` | Citus скрывает шарды (`citus.override_table_visibility=on`) | добавь `SET citus.override_table_visibility = off;` перед SELECT |
